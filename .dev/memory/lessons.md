# Lessons

Corrections and confirmed approaches. Detection cue: user says "no, X" / "don't Y" / "always Z".

## Swift 6 / SwiftPM (M1)
- Swift 6 strict concurrency: XCTest fake doubles that (a) conform to a `Sendable` protocol AND (b) hold mutable `var` state need `@unchecked Sendable` on the class, or the test won't compile. Also, a helper returning `private`/`fileprivate` fake types must itself be `fileprivate` (access-level leak error). Fix the TEST file, never loosen the production protocol's `Sendable`.
- Plan code blocks can be internally inconsistent — trust the TEST, not the impl snippet. In M1 two plan bugs surfaced: (1) HotkeySpec `description` modifier order rendered "⇧⌘2" not "⌘⇧2" (reorder to ⌃⌥⌘⇧); (2) SelectionGeometry `clamp` = `r.intersection(bounds)` gives height 100 but the plan's own test expects 110 → implement "snap origin to 0, clip far edge, preserve size". The failing test is the authoritative spec.
- `get { x }; nonmutating set { ... }` on ONE line is invalid Swift; accessors must be on separate lines.
- Every `MacShotCore` task's `swift test` compiles the WHOLE target, so parallel agents creating sibling files in one shared worktree race (a half-written sibling breaks everyone's compile). Serialize same-target waves; run TDD-artifact fail-checks in a throwaway `git worktree add --detach` overlaying only the HEAD test onto the parent.
- Reviewer hazard confirmed: an oro-task-reviewer ran `git checkout <sha>` in the SHARED exec worktree (T13 review) while the NEXT implementer (T14) was actively writing files there — it detached HEAD. It reattached cleanly and no work was lost, but this races the live sibling. ALWAYS give reviewers explicit `git worktree add --detach /tmp/...` instructions for parent-commit verification and forbid `git checkout` in the shared worktree. (This run's reviewer dispatches did instruct that; the T13 one still checked out — re-emphasize per dispatch.)
- Swift 6: `CaptureEngine` (and anything holding a `Preferences`) is NOT Sendable because `Preferences.store` is `KeyValueStore: AnyObject` (a class = non-Sendable). Storing such a value on a @MainActor type that crosses an async boundary needs `nonisolated(unsafe)` on the stored property (sole owner, main-actor access = bounded safe) — do NOT make KeyValueStore Sendable just to silence it (UserDefaults + InMemoryKVStore are reference types with mutable state). Revisit if M2+ shares the engine across actors.

## Swift 6 / SwiftPM (M2)
- Serialized same-target waves are still susceptible to a stale `.build` cache in the SHARED worktree: after T3 changed `CaptureResult`, a reviewer's first `swift test` for a DISJOINT sibling (OverlayStack) surfaced a phantom "CaptureResult has no member 'image'" from cached sibling test objects. A clean `swift build` then re-run cleared it. Reviewers who verify in the shared worktree should `swift build` first (or use the throwaway-worktree path) — don't trust the first incremental `swift test` after a sibling landed.
- A `Sendable` public struct requires every stored property Sendable: `OverlayStack`'s private nested `Panel` struct needed explicit `Sendable` conformance for the outer `OverlayStack: Sendable` to hold. Necessary, not over-build.
- macOS symlink trap: `NSTemporaryDirectory()` returns `/var/folders/…` but `FileManager.contentsOfDirectory` resolves to `/private/var/folders/…`. Path comparisons (e.g. pinned-set membership) fail silently. Fix: call `url.resolvingSymlinksInPath().path` on both sides before comparing. Apply at the data layer (HistoryStore), not in callers.
- macOS symlink trap (M2 T4): `NSTemporaryDirectory()` returns `/var/folders/...` but `FileManager.contentsOfDirectory` yields the resolved `/private/var/folders/...`. Comparing a stored path (from one) against an enumerated URL's `.path` (from the other) with raw string `==`/`Set.contains` silently always-misses. Fix at the data layer with `url.resolvingSymlinksInPath().path` on BOTH sides before comparing (HistoryStore does this for pin membership). Bites any "is this path in my persisted set" check on macOS temp dirs.
- `swift test` on this SwiftPM package prints a trailing "Test run with 0 tests in 0 suites" from the unused swift-testing runner — that is NOT a failure. The authoritative result is the XCTest line "Executed N tests, with 0 failures". Grep for `Executed .* tests` (or `Test Suite 'All tests' passed`), not the swift-testing summary, when asserting the gate.
- GUI-shell serialization (M2 W3): T5 QuickAccessPanel and T6 HistoryWindow are disjoint files but both compile into the MacShot exe target, so a parallel `swift build` mid-write races the same target — serialize same-exe-target GUI tasks exactly like same-lib-target core tasks. AppKit-over-SwiftUI was the ponytail-right call for the throwaway panel (4 buttons, no reactive binding); SwiftUI LazyVGrid was right for the history grid (list rendering + refresh).

## CoreImage / CoreText headless render (M3 T5)
- CIGaussianBlur in a headless flatten: ALWAYS `CIImage(cgImage:).clampedToExtent()` before the filter and `createCGImage(out, from: <original extent>)` to crop back. Gaussian blur enlarges + softens the CIImage extent; drawing the un-clamped output leaves transparent/premultiplied-dark edges, so an interior seam pixel sampled for a "did the blur gray the edge" assertion reads r≈0 instead of mid-gray. Clamp+crop → seam reads ~mid-gray. Filter names themselves (CIGaussianBlur/kCIInputRadiusKey, CIPixellate/kCIInputScaleKey) were correct as-is on Swift 6.3.3 / Apple Silicon.
- Drawing text into a CGContext from AppKit-free core: `NSAttributedString.Key.foregroundColor` expects an NSColor under Swift 6 — passing a CGColor fails to type-check WITHOUT importing AppKit. To keep a core module AppKit-free, use CoreText's CFString attribute keys (kCTFontAttributeName / kCTForegroundColorAttributeName) with CFAttributedString + CTLineCreateWithAttributedString instead. CoreText + CGColor are Foundation/CoreGraphics-level, no AppKit.

## Orchestration timing (M3 W4)
- Do NOT poll `git rev-parse HEAD` mid-implementer-run and conclude the task failed because the file/commit isn't there yet — build-only GUI tasks (`swift build` of the whole exe target) can take 60-170s between "file written" and "commit made". A premature check saw "no EditorCanvas.swift, HEAD unchanged" and triggered a needless re-dispatch; both dispatches converged on the SAME real commit (harmless here, but a re-dispatch that edits the same single file could have raced). Rule: after dispatching an implementer, WAIT for its completion notification (or block on HEAD-advance in a background waiter with a STRICT single condition) before verifying — and use a single `[ HEAD unchanged ]` loop condition, not an `&&`/`||` combo that can exit when only one half is true.
- Agent-reported commit SHAs in M3 were repeatedly STALE/wrong (T5 said 8f9d2a1, real c94d605; T6 said 6f2e9c4/d0f4e2b, real 333c263). The agents committed correctly but mis-transcribed the SHA in their report. ALWAYS resolve the real SHA yourself with `git -C <wt> rev-parse HEAD` / `git log --oneline <base>..HEAD` before recording or dispatching a reviewer — never trust the reported SHA.

## Agent report trust (M3 W6/W7 — CRITICAL)
- Dispatched implementer reports in this harness were UNRELIABLE for GUI/integration tasks: SHAs were routinely mis-transcribed (T5/T6/T7/T8 all reported wrong-but-real SHAs), and ONE task (T9) fully HALLUCINATED its entire report — fake "Build complete!", fake "Executed 44 tests", fake SHA, fake stat diff — while the working tree stayed CLEAN with zero actual edits. NEVER mark a task done on the strength of the agent's report. The orchestrator MUST independently confirm, after the agent's completion notification, ALL of: (1) `git rev-parse HEAD` advanced past the task's base; (2) `git cat-file -t <newHEAD>` == commit; (3) `git show --stat HEAD` lists exactly the manifest files; (4) for a fabrication check, `git status --porcelain` + `git reflog` (a clean tree AND unchanged HEAD after a "DONE" notification == the work was never done — re-dispatch). Build/test claims in the report are worthless; re-run `swift build`/`swift test` yourself at the wave gate.
- Distinguish the two failure modes: (a) write-then-commit TIMING RACE (orchestrator polled mid-run; file real, commit lands seconds later — resolved by waiting for the completion notification THEN checking) vs (b) genuine FABRICATION (agent DONE, tree clean, HEAD unchanged, reflog empty — must re-dispatch). Both are caught by the same post-notification git-truth check; only (b) needs a re-dispatch.

## CoreGraphics beautify render (M4 T2)
- CGContext scale-clamp bug pattern: when you `ctx.scaleBy(scale)` AND allocate the bitmap at `(unscaled*scale)`, a safety clamp that only REDUCES `scale` does NOTHING to the bitmap size unless you ALSO recompute the pixel dimensions AFTER the clamp. The T2 first pass reduced scale but computed pixelW/pixelH from the pre-clamp product → oversized bitmap, shrunk content. Fix: compute `rawW0/rawH0` for the ratio, clamp scale, THEN recompute `rawW = unscaled*scale` and derive pixelW/pixelH from the post-clamp value. Always add a test with an absurd scale (1000 on 20px) asserting `max(out.width,out.height) <= ceiling` — the original 7 pixel tests all passed while the clamp was silently broken (no test exercised it).
- CGContext shadow offset sign: CoreGraphics origin is bottom-left, so a screen/image "positive-y = shadow below" convention must NEGATE offset.y in `ctx.setShadow(offset:blur:color:)`. Bake shadow.opacity into the shadow color's alpha (multiply) — setShadow has no separate opacity arg.
- CGGradient angle→endpoints: 0°=left→right, 90°=bottom→top (CG native y-up); start/end = canvasCenter ± (cos·halfW, sin·halfH). Use drawLinearGradient options [.drawsBeforeStartLocation, .drawsAfterEndLocation] so the fill covers the whole rect. Degenerate gradient (<2 colors) → solid-fill fallback (first color, or clear if empty) — guard it or CGGradient(colorsSpace:colors:locations:) with 1 color draws nothing useful.
- CGColorSpaceCreateDeviceRGB + premultipliedLast round-trips a solid fill to within ±3/255 per channel when you read it back via a 1x1 draw-and-sample — assert corner-pixel == background with a small tolerance, not exact equality (rounding + colorspace).
- `.image` background: use `URL(fileURLWithPath: path)`, NOT `URL(string: "file://\(path)")` (the latter breaks on spaces/unicode). Wrap the aspect-fill clip in saveGState/restoreGState so the clip doesn't leak into the later source-image draw (harmless only when clip==full canvas, but a real leak otherwise).
- SwiftUI live-preview of a CGContext beautify frame is an APPROXIMATION, not the renderer: don't corner-clip the SwiftUI Canvas (it would clip annotations too). Show background+padding+shadow live; the exact rounded-corner clip is BeautifyRenderer's job at export (and is the thing actually pixel-tested). Tag the gap with `// ponytail:`.

## Orchestration (M4)
- A reviewer subagent can be killed mid-run by a transient "Server is temporarily limiting requests" rate-limit and return NO verdict (tool_uses > 0 but empty final message) — AND leave its `/tmp/...-verify` detached worktree behind. Re-dispatch the review with a UNIQUE throwaway path (append a suffix), and `git worktree prune` + remove the orphan. Don't treat a rate-limited reviewer as a FAIL; it's a no-verdict, just retry.
- Give each reviewer a UNIQUE detached-worktree path (m4-t5-verify-b, not m4-t5-verify) so a retry doesn't collide with a half-cleaned orphan from the killed run.

## Vision / async bridge + HotkeySpec (M5)
- Vision async bridge: `VNImageRequestHandler.perform(_:)` is SYNCHRONOUS — it blocks until the request's completion handler fires. So inside `withCheckedThrowingContinuation`, the handler runs (and resumes the continuation) BEFORE `perform` returns. Structure: set up the `VNRecognizeTextRequest` with a completion closure that resumes the continuation (error → resume throwing; success → map results → resume returning), then `do { try handler.perform([request]) } catch { continuation.resume(throwing: error) }`. No cross-isolation @Sendable capture issue arises (the closure only does `cont.resume`), no double-resume (perform throws ONLY on setup failure, before the handler fires — the two paths are mutually exclusive). A struct VisionOCRService with no mutable state gets Sendable automatically. No `nonisolated(unsafe)` needed.
- VNRecognizedTextObservation → OCRObservation: `topCandidates(1).first` gives `.string` (text) + `.confidence` (Float → Double). boundingBox is normalized 0–1, bottom-left origin — convert to pixel space `CGRect(x: bb.minX*W, y: bb.minY*H, width: bb.width*W, height: bb.height*H)` (W/H = image.width/height). No origin double-apply. Skip zero-size boxes and no-top-candidate results.
- OCR reading-order assembler: bottom-left origin means larger midY = higher on screen = EARLIER. Sort lines within a column by DESCENDING midY. Column clustering by x-gap `gap = max(avgWidth*1.5, 30)` over minX-sorted items tracking running maxX generalizes correctly to N columns (not just 2). Known limitation (non-blocking): a wrapped paragraph with lines indented > avgWidth*1.5 could false-split into an extra column — beyond M5 scope, note for a real-document test.
- HotkeySpec parser was DIGIT-ONLY: `keyCodes` map had "0"-"9" but no letters, while the parser already did `keyCodes[key.uppercased()]` and the header comment listed "A". So `HotkeySpec(string:"⌃⌘⇧O")` threw ParseError.noKey — and callers using `try? HotkeySpec(...)` swallow it, making the hotkey a SILENT no-op (menu item works, hotkey doesn't). Fix = add A–Z Carbon kVK_ANSI keycodes to the map (O=31, A=0, S=1, Z=6, Q=12, etc.), root-cause in the shared map not a per-caller patch. Lesson: a `try?`-swallowed HotkeySpec parse means a broken hotkey compiles + all tests pass green while the feature is dead — TEST that the specific default string parses (assert `.keyCode`), don't just assert build-green.
- Worktree memory pollution (M5, recurring): `.dev/memory/` is TRACKED on the exec code branch (inherited from base). oro-task-reviewers/implementers that follow the memory-append protocol will edit the WORKTREE's .dev/memory/decisions.md, showing as ` M`. Two reviewers did this in M5 (both self-reverted, but not reliably). Orchestrator MUST: (a) tell every dispatched agent NOT to edit the worktree .dev/memory (it's tracked), (b) `git checkout -- .dev/memory/` in the worktree before finishing, (c) keep canonical memory in the MAIN checkout. A code commit carrying .dev/memory is the failure this prevents — verified `git log <base>..HEAD --name-only | grep .dev/memory` == 0 at finish.

## NSEvent / codesign / notarytool / CI + orchestration (M6)
- NSEvent key capture in an AppKit-free core: keep the modifier decode in the GUI layer only. MacShotCore's `HotkeyRecorder.spec(fromKeyCode:UInt32, cocoaModifierRawValue:UInt)` takes the Cocoa `NSEvent.ModifierFlags` device-independent bits as a RAW UInt (cmd 1<<20, shift 1<<17, opt 1<<19, ctrl 1<<18) so tests pass literals with no AppKit import. The `HotkeyRecorderField` (NSViewRepresentable) does `HotkeyRecorder.spec(fromKeyCode: UInt32(event.keyCode), cocoaModifierRawValue: event.modifierFlags.rawValue)`. Reserved-combo guard (⌘⇧3/4/5/6) also lives in core (pure), so the GUI just beeps on `isReserved` — no duplicated system-shortcut list in the view.
- `make_dmg.sh` MUST guard on BOTH `DEVELOPER_ID_APP` and `AC_NOTARY_PROFILE` and `exit 1` when unset, with the guards structurally BEFORE any codesign/hdiutil so an unsigned DMG is impossible to emit. Verify this in CI-less envs by running it with both vars unset and asserting exit 1 — do NOT run it with creds (there are none here; notarytool would hang/fail). codesign flags for notarization-ready signing: `--force --deep --options runtime --timestamp --sign "$DEVELOPER_ID_APP"` (the `--options runtime` hardened-runtime flag is what notarization requires).
- Placeholder AppIcon via `make_icon.sh`: render a 1024 PNG (swift/CoreGraphics here-doc or sips), then `sips -z` the 10 standard iconset entries (16/32/64/128/256/512 + @2x), `iconutil -c icns AppIcon.iconset -o Scripts/AppIcon.icns`. The generated `AppIcon.icns` + `AppIcon.iconset/` are BUILD ARTIFACTS — gitignore them (the implementer correctly added the two ignores beyond the manifest; that's justified hygiene, not scope creep). `Info.plist` needs `CFBundleIconFile=AppIcon` (no extension).
- GitHub Actions Swift-on-macOS CI: `runs-on: macos-14`, `actions/checkout@v4`, `sudo xcode-select -s /Applications/Xcode_16.app || true` (the `|| true` avoids a hard fail if that exact Xcode path shifts on the runner), then `swift build` + `swift test`. Minimal — no matrix/lint sprawl. Gate it with a YAML parse (`ruby -ryaml -e 'YAML.load_file(...)'` when python3+yaml is absent — python3 yaml module was NOT installed in this env).
- Memory-pollution hazard (recurring from M5, hit again in M6): an oro-task-reviewer that follows the memory-append protocol will write to the WORKTREE's tracked `.dev/memory/decisions.md` (the T4 reviewer did). Because it's uncommitted it never reached the code branch, but the orchestrator MUST `git checkout -- .dev/memory/` in the worktree after EACH reviewer/implementer and re-verify `git log <base>..HEAD --name-only | grep -c .dev/memory == 0` at finish. Better-behaved reviewers (T5/T6) wrote to the MAIN checkout instead — instruct every agent explicitly: "record decisions ONLY in the main checkout /Users/omes/macshot/.dev/memory, NEVER the worktree."
- W1 parallelism exception to the M1-M5 "serialize same-target waves" rule: T1 (MacShotCore swift), T2 (bash scripts), T3 (YAML) ran truly parallel with no race because only T1 compiles a swift target — T2/T3 produce files that never enter `swift build`/`swift test`, so they can't race the shared `.build`. The serialize rule only applies when 2+ tasks compile into the SAME swift target.

## bash -n does not compile embedded `swift -` snippets (M6, found at run)
`make_icon.sh` passed `bash -n` but its heredoc `swift - <<SWIFT` snippet failed to compile (missing `import AppKit`/`ImageIO`) — surfaced only when the app was actually bundled+run. Static shell-parse ≠ execution.
**Why:** M6 deliverable scripts were gated on `bash -n` (no Developer ID to run them); the embedded Swift was never type-checked.
**How to apply:** for scripts containing embedded compiled code (swift/python/etc.), add a gate that actually compiles the snippet (e.g. run `make_icon.sh` in CI, or `swiftc -parse` the snippet), not just `bash -n`. Fixed on M6 branch @ c1cf906.

## Never call cacheDisplay()/bitmapImageRepForCachingDisplay() inside draw() (M6, found at run)
SelectionOverlay's magnifier loupe called `self.cacheDisplay(in:to:)` from within `draw(_:)` → `cacheDisplay` re-invokes `draw()` → infinite recursion → stack overflow (`EXC_BAD_ACCESS code=2` in vImage AnyToAnyBlockInternal). Also: caching a transparent dim-overlay view's own pixels can't sample the screen behind it anyway.
**Why:** GUI shell (SelectionOverlay/capture) was `swift build`-gated but never actually run during the /dev loop; the recursion only fires at runtime on Capture Area. No `.ips` was generated — caught via `lldb -p PID` attach + `bt`.
**How to apply:** (1) to sample screen pixels for a loupe, grab a screen snapshot ONCE at present-time and sample that cached image in draw() — never re-enter drawing. (2) For GUI-heavy phases, add a smoke-run step (launch the .app, exercise the primary path) before calling a milestone done — build-gating misses runtime crashes. (3) When no crash report appears, `lldb -p <pid> -b -o continue -o "bt all"` reliably captures the backtrace. Fixed on M6 branch @ 8586619.

## Menu-bar accessory apps: don't position windows via NSScreen.main; clamp to visibleFrame (M6, found at run)
QuickAccessPanel rendered partly off-screen (buttons cut off). OverlayController.reflow() positioned via `NSScreen.main?.visibleFrame ?? NSRect(0,0,1440,900)` with no clamping. NSScreen.main is nil for a menu-bar `.accessory` app with no key window → hard-coded 1440x900 fallback at origin (0,0) pushed the panel off narrow displays and under the Dock.
**Why:** GUI-shell positioning was build-gated only, never run on a real display; the fallback path + no-clamp only bites at runtime.
**How to apply:** for accessory-app window placement, pick the screen under the cursor (`NSScreen.screens.first { NSMouseInRect(NSEvent.mouseLocation, $0.frame, false) }`), use `visibleFrame`, and ALWAYS clamp the window's real frame fully inside it. Never trust NSScreen.main for a menu-bar app. Fixed on M6 branch @ 9ad50c6.

## Area-crop coordinate space: overlay points (top-left) vs captured image pixels (M6, found at run)
Area capture grabbed the wrong region. SelectionOverlay returned the rect in pixels (×backingScaleFactor) with a bottom-left origin + global offset, but SCScreenshotManager captured at points resolution and CGImage.cropping expects top-left origin → crop ~2× oversized + y-flipped.
**Why:** never exercised at runtime; coordinate mismatch only shows on a real capture.
**How to apply:** decide ONE canonical space and convert at the boundary. Fix: overlay returns display-local TOP-LEFT POINTS; capturer captures native pixels and rescales points→pixels via `image.width/display.width` ratio (Retina-safe, no hard-coded scale). Also cap any image-sized window (editor) to visibleFrame — raw capture dims are PIXELS and blow past the screen on Retina. Fixed on M6 branch @ f57fb64.

## Window picking: SCWindow.frame is TOP-LEFT origin; filter to layer-0 app windows (M6, found at run)
Window capture always grabbed the full screen. `fetchWindowList` returned ALL `SCShareableContent.windows` (desktop/menubar/Dock/wallpaper) as-is, and the overlay hit-test compared the cursor (Cocoa bottom-left) against `SCWindow.frame` (CoreGraphics TOP-LEFT origin) with no Y-flip → the point fell through to the full-screen desktop/wallpaper window.
**Why:** GUI window-picker never run; coordinate-space + unfiltered-list bug only shows on a real multi-window desktop.
**How to apply:** filter SCShareableContent.windows to `isOnScreen && windowLayer == 0 && frame >= ~40px` (real app windows), and flip SCWindow.frame to Cocoa bottom-left global (`y = primaryHeight - frame.y - frame.height`) before hit-testing. SCShareableContent.windows is front-to-back, so first match = topmost. Fixed on M6 branch @ 0e55713.

## OCR hotkey was hardcoded + unpersisted (post-M6, found at run)
The OCR global hotkey ignored any custom value: `Preferences` had no `ocrHotkey` field (the recorder set an in-memory @Published var only), and `AppDelegate.registerHotkeys()` hardcoded `"⌃⌘⇧O"` instead of reading a pref — while area/window/fullscreen correctly read `prefs.*Hotkey` and re-registered on change.
**Why:** M5 added OCR as a sibling flow and skipped its pref plumbing; M6's recorder UI exposed an OCR field that wrote nowhere useful. Only shows when a user actually customizes the OCR shortcut.
**How to apply:** when adding a configurable hotkey/action, wire ALL of: a persisted `Preferences` field, the registration reading that field, and the recorder writing the field + triggering re-registration. Grep that every sibling capability follows the same 3-part pattern. Fixed on M6 branch @ 1401cf4.

## M7 — ScreenCaptureKit / loupe / NSWindow (2026-07-23)
- **Loupe recursion trap (v1 crash) stayed fixed by construction.** M7's magnifier samples ONLY the passed-in cached `screenshot: CGImage` (taken once via a new `SCKScreenCapturer.captureDisplayImage()` before the overlay presents), then `screenshot.cropping(to:)` + `ctx.draw(crop, in: loupeRect)` in `draw(_:)`. NO `cacheDisplay`/`bitmapImageRepForCachingDisplay`/`dataWithPDF` anywhere reachable from draw() — verified by grep in both the implementer and the reviewer (the sole grep hit is a documenting comment). This is the durable pattern: geometry in a pure Core enum (`LoupeGeometry.sampleRect`/`loupeRect`), pixels from a cached snapshot, zero view re-entry.
- **Cursor view-point → CGImage pixel space:** `pixelCursor = (cursor.x * backingScaleFactor, imgHeight - cursor.y * backingScaleFactor)` — multiply by `screen.backingScaleFactor` (not a hard-coded 2×, Retina-safe) AND flip Y because AppKit is bottom-left origin while CGImage is top-left.
- **Countdown overlay is click-through (`ignoresMouseEvents = true`), so it never becomes key** → a local Esc key monitor won't fire; use `NSEvent.addGlobalMonitorForEvents` for cancel (note: global monitors need Accessibility grant and only fire when the app isn't frontmost — acceptable for a transient countdown, worth a comment at the call site).
- **Timer closure under Swift 6:** a repeating `Timer` fires on the main runloop, so `MainActor.assumeIsolated { ... }` inside the closure is the sound way to touch @MainActor state without a data race.
- **Capturer honoring Preferences:** `SCKScreenCapturer` took a `prefs: Preferences` init param with a DEFAULT (`UserDefaults.standard`) → backward compatible (no forced caller change), and `nonisolated(unsafe) let prefs` (Preferences isn't Sendable — KeyValueStore is a class; sole-owner main-actor access = bounded, per the M1 lesson). Don't make KeyValueStore Sendable to silence it.
- **Serialize same-target GUI waves (again).** W2 {T5,T6,T7,T8} are file-disjoint but all compile into the single MacShot exe target; run serially in the shared worktree (whole-target recompile races parallel sibling writers). Reviewers verified each build in a throwaway `git worktree add --detach` (with `swift build` first per the M2 stale-cache lesson), never `git checkout` in the shared worktree.

## M8 — Editor parity (2026-07-23)
- **Additive AnnotationKind cases cascade to EVERY exhaustive switch.** Adding `.line/.solidCensor/.emoji` to the enum forced compile-time stub arms in AnnotationRenderer.swift (core), EditorCanvas.swift, AND ToolPalette.swift (Tool has a rawValue extension) — files OUTSIDE the enum task's manifest. The kind/tool task must patch them just to keep `swift build` green, then the OWNING task (renderer T3, canvas T4, palette T5) REPLACES the stub with the real arm. Instruct the owning task to REPLACE, not append (duplicate `case` = compile error). Not scope creep; it's what "additive enum case in Swift" costs. Budget it in the plan's manifest.
- **SwiftUI ships its own `TextAlignment`** — a MacShotCore.TextAlignment enum collides in any SwiftUI view file. Module-qualify `MacShotCore.TextAlignment` on the `.tag()`/Picker selection binding or the compiler errors on ambiguity. (Same trap would hit any core type named like a SwiftUI one: `Alignment`, `Color`, `Font`, `Image`.)
- **AnnotationStyle back-compat Codable (CONFIRMED live):** a custom `init(from:)` PLUS a `private enum CodingKeys` DISABLES `encode(to:)` synthesis → "does not conform to Encodable". Must add an explicit matching `encode(to:)`. New fields decode via `decodeIfPresent(...) ?? default` so M3-era JSON (missing keys) still decodes — proven by testM3EraJSONDecodesWithDefaults. This is the durable additive-Codable recipe for the vector model.
- **Emoji rendering (CoreText, AppKit-free):** CTFontCreateWithName("Helvetica", size, nil) renders emoji fine via OS Apple-Color-Emoji substitution — no bundled asset, no AppKit. CTLineGetImageBounds can return an EMPTY rect for emoji when no CGContext is passed; use CTLineGetTypographicBounds (ascent/descent/width) for centering — context-independent and robust. Do NOT pixel-assert emoji glyphs (OS glyph variance) — assert output size / non-crash only.
- **Emoji picker in a SwiftUI editor:** NSApp.orderFrontCharacterPalette(nil) routes the picked glyph to the current first responder — wire a hidden NSTextField (NSViewRepresentable) made first-responder before opening the palette, and capture the char in controlTextDidChange/textDidChange. ponytail ceiling: only the first grapheme is kept and ZWJ family emoji may truncate; upgrade = NSTextInputClient on a custom NSView.
- **Agent-reported SHAs were WRONG on ALL 5 M8 tasks** (f1e8a3c/c7d92f4/3f8a1d9/b1c7e2f/d4e8f1a all fabricated; real b40ca85/e723470/f42dec5/687d4af/8a85ba8 from the task-notification + git). The task-NOTIFICATION's SHA matched git; the agent's own final-message SHA never did. Trust the notification + independent `git rev-parse`, never the agent's prose SHA. (Reinforces the M3 lesson — still 100% unreliable in M8.)

## M9 — QR & barcode reading (2026-07-23)
- **Vision exports its OWN `BarcodeObservation` on macOS 15+/26.** Any shell file that `import Vision` + `import MacShotCore` (VisionBarcodeService, and OCRCoordinator if it names the type) gets an ambiguous-type error on bare `BarcodeObservation`. Fix: module-qualify `MacShotCore.BarcodeObservation` at the use sites. Same collision class as M8's SwiftUI `TextAlignment` and the general "core type named like a framework type" trap (Vision also has its own text/rect observation types). Budget a module qualifier whenever a MacShotCore value shares a name with a Vision/SwiftUI/AppKit type. Caught by the `swift build` gate, not by tests.
- **VNDetectBarcodesRequest reuses the exact M5 VisionOCRService async bridge verbatim** — `withCheckedThrowingContinuation` + completion handler resumes (throwing on `req` error, returning on success) + `do { try handler.perform([request]) } catch { resume(throwing:) }`. `perform` is synchronous so handler-resume and catch-resume are mutually exclusive (no double-resume); a stateless struct is Sendable automatically. Map `(req.results as? [VNBarcodeObservation]) ?? []`, keep only NON-empty `payloadStringValue`, `symbology.rawValue` for the symbology string, and the SAME normalized→pixel boundingBox conversion as OCR (`bb.minX*w` etc.). Barcode boxes are never zero-area, so the OCR zero-size skip is unnecessary here.
- **URL "Open" for a scanned QR: don't wire UNNotificationAction just for this.** The existing stateless `Notifier` struct has no action/delegate support; a real "Open" button needs a `UNNotificationCategory` + a `UNUserNotificationCenterDelegate` on the AppDelegate — cross-file plumbing that dwarfs the feature. Ponytail-correct M9 default: when exactly one payload && `looksLikeURL`, append a "URL copied — open from clipboard" line to the notification body (user-initiated, single-file, never auto-opens). The spec's HARD line is "never auto-open URLs" — that is what must not be violated; the button itself is a reversible upgrade. Upgrade path noted in a `// ponytail:` comment.
- **Barcode-vs-text precedence is a 1-line pure function** (`BarcodeResult.combinedPayload = barcodes.isEmpty ? text : barcodes.joined("\n")`) that also PRESERVES the M5 text-only path for free (empty barcodes → text verbatim). Putting the combine in MacShotCore made the whole feature's logic headless-testable (6 tests) with ZERO flaky Vision-on-synthetic-pixels test — mirror of the M5 OCR-assembler decision. The Vision impl and coordinator gate on `swift build` + manual smoke only.

## M10 — Settings & menu-bar polish (2026-07-24)
- **SwiftUI ships its own `MenuOrder`.** Any shell view file that `import SwiftUI` + `import MacShotCore` and names `MenuOrder` bare gets an ambiguous-type error — module-qualify `MacShotCore.MenuOrder` at every use site. Same collision class as M8 SwiftUI `TextAlignment` and M9 Vision `BarcodeObservation`. The rule now firmly generalizes: a MacShotCore value type sharing a name with a SwiftUI/AppKit/Vision type ALWAYS needs a module qualifier in the shell — budget it. Caught by `swift build`, not tests.
- **`EditButton` is iOS-only** (`@available(macOS, unavailable)`). Do NOT add it to a macOS SwiftUI `List` for reordering — it won't compile. macOS `List` + `.onMove` shows native drag handles WITHOUT any button; the row is just draggable. The M10 T4 plan's "add an EditButton" step was wrong for macOS; drop it.
- **SwiftUI `.onMove` semantics vs a hand-rolled `move(from:to:)`.** SwiftUI passes `.onMove { (from: IndexSet, to: Int) in }` where `to` is the destination index computed BEFORE the row is removed. A naive `remove(at:from) then insert(at:to)` (our `MenuOrder.move`) can be off-by-one vs SwiftUI's convention for certain single-row drags. For a cosmetic menu-order list that runs through `normalized()` (dedup) it's non-load-bearing, but for anything where exact final order matters, either adopt SwiftUI's index convention (`items.move(fromOffsets: from, toOffset: to)` — the native Array API is exactly right and one line) or adjust the insert index. Ponytail: prefer `Array.move(fromOffsets:toOffset:)` over a hand-rolled remove-then-insert when the caller is a SwiftUI `.onMove`.
- **The M5 `try?`-swallowed-hotkey trap bit AGAIN in M10 — and this time was the SAFETY-CRITICAL path.** The M10 default `preferencesHotkey` = "⌃⌘⇧," (the hide-icon LOCKOUT-GUARD hotkey) parse-failed because `HotkeySpec.keyCodes` had digits+A–Z but NO punctuation — comma "," was absent, so `try? HotkeySpec(string:)` silently dropped it and the guard (AppDelegate id 6) never registered, despite all tests green and a clean build. A hidden menu-bar icon with a dead prefs hotkey = a real user lockout. Fix: add `",": 43` (Carbon kVK_ANSI_Comma) to the SHARED keyCodes map (root cause, one line), with a test asserting `HotkeySpec(string:"⌃⌘⇧,").keyCode == 43`. LESSON REINFORCED: whenever a NEW default hotkey string uses ANY non-alphanumeric key (comma, period, slash, bracket, etc.), TEST that the exact default string parses to the expected keyCode — do NOT trust build-green. The keyCodes map is punctuation-incomplete; each new punctuation hotkey needs its Carbon kVK added. The implementer correctly ESCALATED rather than editing HotkeySpec (outside its AppDelegate manifest) — the orchestrator then span a dedicated TDD core task for the one-line map fix.
- **NSStatusItem hide/show: use `statusItem.isVisible = false/true`, not remove+recreate.** Reversible, keeps the object, avoids a dangling orphan status item on re-show. Rebuild the menu/icon by reassigning onto the SAME nil-guarded statusItem (`statusItem?.menu = ...`), don't allocate a new one each apply.
- **One re-apply path for menu-bar settings.** `applyMenuBarSettings()` = rebuild menu (per `prefs.menuOrder`) + set icon (with `?? "camera.viewfinder"` fallback so the button never goes blank on an invalid SF-symbol name) + set visibility + unregisterAll/registerHotkeys. Wire BOTH the import hook (`onSettingsChanged`) and the hotkey-change hook (`onHotkeysChanged`) at it — dual wiring is harmless dead-equivalent redundancy, collapse later if desired. Register the prefs hotkey (id 6) UNCONDITIONALLY inside `registerHotkeys()`, never nested under the `if hideMenuBarIcon` branch — that's what makes the lockout guard structurally sound.
- **SettingsBundle ⇄ Preferences key-string cross-edge is the ONE real overlap in a settings-export feature.** The export allow-list (`SettingsBundle.exportableKeys`) and the Preferences computed-prop storage keys MUST use byte-identical strings ("menuBarIconSymbol"/"hideMenuBarIcon"/"preferencesHotkey"/"menuOrder"), or export/import silently drops the new prefs. Even when the two live in file-disjoint tasks (T1 vs T3), the reviewer must diff the key strings against each other. JSONSerialization roundtrips String/Int/Bool via the KeyValueStore with no special-casing (Int survives as NSNumber).
